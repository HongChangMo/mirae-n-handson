# legacy/item-bank-php 비즈니스 규칙 후보

> 선행 문서: [ARCHITECTURE.md](ARCHITECTURE.md), [ERD.md](ERD.md).
> 근거는 `legacy/item-bank-php/` 기준 `파일:줄번호` 다. 스키마 · 시드는 `db/mariadb/init/01-schema.sql`, `02-seed.sql` 로 적는다.
> 확신도: **확실** = 조건문 · SQL 로 확인 / **추정** = 이름 · 주석 · 스키마 설정으로 짐작.
> 코드에 없는 규칙은 적지 않았다. 주석에만 있는 내용은 규칙으로 올리지 않고 8절에 모았다.

## 0. 요약

| 영역 | 규칙 ID | 핵심 |

| 검색 대상 · 조건 조합 | BR-01 ~ BR-16 | 공개(`status='A'`) 문항만, 조건은 AND. **난이도가 비면 난이도 5 제외**(BR-10) |

## 1. 문항 검색 — 대상과 조건 조합 (`search.php`)

### BR-01 공개 문항만 검색
- **규칙**: 문항의 `status` 가 `'A'` 가 아니면 검색 결과(목록 · 건수)에서 제외한다.
- **근거**: `search.php:522`, `search.php:526`, `db/mariadb/init/01-schema.sql:70`
- **근거 코드**:
  ```php
  $from   = " FROM v_item_public";                      // search.php:522
  ```
  ```sql
  WHERE i.status = 'A';                                   -- 01-schema.sql:70
  ```
- **확신도**: 확실
- **비고**: 제외 조건이 코드가 아니라 뷰 정의에 있다. 이관 시 뷰를 쓰지 않으면 이 조건이 빠지기 쉽다. 뷰는 `unit` 과 INNER JOIN(`01-schema.sql:69`)이지만 FK · NOT NULL 때문에 추가로 빠지는 행은 없다(ERD.md 4절).

### BR-02 검색 조건은 모두 AND 로 결합
- **규칙**: 키워드 · 단원 · 난이도 · 태그 조건이 여러 개 주어지면 모두 만족하는 문항만 찾는다(AND).
- **근거**: `search.php:44`, `search.php:98`, `search.php:118`, `search.php:215`, `search.php:218`, `search.php:226`, `search.php:244`
- **근거 코드**:
  ```php
  $where    = " WHERE 1=1";
  $where .= " AND (title LIKE ? OR stem LIKE ?)";
  $where .= " AND unit_code = ?";
  ```
- **확신도**: 확실
- **비고**: OR 조합이나 다중 값(단원 여러 개, 태그 여러 개) 검색 경로는 없다 (BR-03).

### BR-03 파라미터가 배열이면 첫 값만 사용
- **규칙**: `q` · `unit` · `level` · `tag` · `sort` · `dir` · `page` 가 배열(`?tag[]=a&tag[]=b`)로 들어오면 첫 값만 쓴다.
- **근거**: `search.php:55`, `:59`, `:63`, `:67`, `:71`, `:75`, `:79`
- **근거 코드**:
  ```php
  $tag = is_array($params['tag']) ? (string)reset($params['tag']) : (string)$params['tag'];
  ```
- **확신도**: 확실
- **비고**: 태그 · 단원 다중 선택은 지원하지 않는다는 뜻이다.

### BR-04 키워드는 제목 · 지문 부분 일치
- **규칙**: 키워드를 앞뒤 공백 제거 후 비어 있지 않으면, `title` 또는 `stem` 에 키워드가 포함된 문항을 찾는다.
- **근거**: `search.php:85`, `search.php:90`, `search.php:97-98`
- **근거 코드**:
  ```php
  $like = '%' . $q . '%';
  $where .= " AND (title LIKE ? OR stem LIKE ?)";
  ```
- **확신도**: 확실
- **비고**: 공백만 입력하면 조건 없음과 같다. 대소문자 구분 여부는 컬럼 콜레이션(`utf8mb4_unicode_ci`, `01-schema.sql:33`)을 따른다 → 구분하지 않을 것으로 **추정**.

### BR-05 키워드 100자 초과 시 잘라서 검색
- **규칙**: 키워드가 100자(문자 수)를 넘으면 앞 100자만 쓰고 경고를 표시한다.
- **근거**: `search.php:86-88`, `search.php:494`
- **근거 코드**:
  ```php
  if (mb_strlen($q, 'UTF-8') > 100) {
      $q = mb_substr($q, 0, 100, 'UTF-8');
  ```
- **확신도**: 확실
- **비고**: 매직 넘버 `100`. 같은 상한이 폼 `maxlength="100"`(`search.php:494`)에도 따로 있다(두 곳 구현).

### BR-06 키워드의 `%` · `_` 는 와일드카드로 동작
- **규칙**: 키워드에 `%` 또는 `_` 가 있으면 이스케이프하지 않고 LIKE 와일드카드로 쓰며, 경고만 표시한다.
- **근거**: `search.php:94-95`, `search.php:97`
- **근거 코드**:
  ```php
  if (strpos($q, '%') !== false || strpos($q, '_') !== false) {
      $warnings[] = '키워드의 % 와 _ 는 와일드카드로 처리됩니다.';
  ```
- **확신도**: 확실
- **비고**: 이관 시 이 동작을 유지할지(문자 그대로 검색으로 바꿀지) 결정이 필요하다.

### BR-07 한 글자 키워드는 경고만
- **규칙**: 키워드가 한 글자면 경고를 표시하고 검색은 그대로 한다.
- **근거**: `search.php:91-92`
- **근거 코드**:
  ```php
  if (mb_strlen($q, 'UTF-8') === 1) {
      $warnings[] = '키워드가 한 글자라 결과가 많을 수 있습니다.';
  ```
- **확신도**: 확실
- **비고**: 최소 길이 제한은 없다.

### BR-08 단원은 단원 코드 정확 일치
- **규칙**: 단원 코드를 앞뒤 공백 제거 후 비어 있지 않으면, `unit_code` 가 그 값과 같은 문항만 찾는다.
- **근거**: `search.php:109-110`, `search.php:118-120`
- **근거 코드**:
  ```php
  $where .= " AND unit_code = ?";
  ```
- **확신도**: 확실
- **비고**: 단원 **id** 가 아니라 **code** 로 검색한다(등록은 id 를 받는다, BR-34). `unit` 테이블 콜레이션이 `_ci`(`01-schema.sql:18`)라 `m5-1` 도 `M5-1` 과 일치할 것으로 **추정**(실행 확인 필요). 그렇다면 경고 문구 "대문자로 입력하세요"(`search.php:116`)와 달리 결과는 나온다.

### BR-09 단원 코드가 잘못돼도 조회는 그대로
- **규칙**: 단원 코드가 형식(`영문1자 + 숫자1~2 + '-' + 숫자1~2`)에 맞지 않거나, 소문자가 섞였거나, `unit` 테이블에 없으면 경고만 표시하고 입력값 그대로 조회한다.
- **근거**: `search.php:111-113`, `search.php:115-116`, `search.php:141-142`
- **근거 코드**:
  ```php
  if (!preg_match('/^[A-Za-z][0-9]{1,2}-[0-9]{1,2}$/', $unit)) {
      // 형식이 달라도 그대로 조회한다 (결과는 대개 0건)
  ```
- **확신도**: 확실
- **비고**: 형식 정규식의 `{1,2}` 가 단원 코드 체계(학년 · 단원 번호 두 자리까지)를 암시한다 — **추정**. 오류(400)가 아니라 경고 + 0건 처리다.

### BR-10 난이도가 비어 있으면 난이도 5 문항을 제외
- **규칙**: 난이도 파라미터가 비어 있으면(없음 · 빈 문자열 · 공백) `level < 5` 조건을 붙여 난이도 5 문항을 결과에서 뺀다.
- **근거**: `search.php:211`, `search.php:214-215`, `db/mariadb/init/02-seed.sql:34`
- **근거 코드**:
  ```php
  // 난이도 값이 비어 있으면 전체 난이도 검색 (1~5 모두 포함)
  if ($level == '') {
      $where .= " AND level < 5";
  ```
- **확신도**: 확실
- **비고**: **주석과 코드 불일치.** 주석(`search.php:213`)과 폼 선택지 "전체"(`search.php:192`), 파라미터 설명 "빈값 허용"(`search.php:8`)은 1~5 전체를 뜻하지만 코드는 1~4 만 찾는다. 시드 주석 `02-seed.sql:34` "status='A' AND level<5 는 정확히 20건" 이 이 동작을 전제로 데이터를 맞춰 두었다. 매직 넘버 `5`. 요약(`$summary`)에 난이도 항목이 추가되지 않아 화면에는 "조건 없이 검색했습니다"(`search.php:356`)로 보일 수 있다. 결과적으로 난이도 5 문항은 `level=5` 를 명시했을 때만(BR-11) 조회된다. 버그인지 의도인지 사람 확인 필요.
  `$level == ''` 는 느슨한 비교지만 `$level` 이 문자열로 변환 · trim 된 뒤라(`search.php:63`, `search.php:211`) 양쪽 모두 문자열이므로 `'0'` 은 빈 값으로 취급되지 않고 BR-12 로 간다 — 동작에 영향 없음.

### BR-11 난이도 1~5 는 해당 난이도만
- **규칙**: 난이도가 `1`~`5` 한 자리 숫자이면 그 난이도와 같은 문항만 찾는다.
- **근거**: `search.php:217-220`
- **근거 코드**:
  ```php
  else if (preg_match('/^[1-5]$/', $level)) {
      $where .= " AND level = ?";
  ```
- **확신도**: 확실
- **비고**: 범위 검색(이상 · 이하)은 없다. 등록 검증과 같은 정규식이다(`register.php:70`).

### BR-12 범위 밖 난이도는 경고 후 정수 변환 값으로 비교
- **규칙**: 난이도가 비어 있지 않고 `1`~`5` 한 자리가 아니면, 경고를 표시하고 `(int)` 로 바꾼 값과 같은 문항을 찾는다.
- **근거**: `search.php:223-229`
- **근거 코드**:
  ```php
  $warnings[] = '난이도는 1~5 사이여야 합니다.';
  $where .= " AND level = ?";
  $values[] = (int)$level;
  ```
- **확신도**: 확실
- **비고**: 주석(`search.php:224`) "대개 0건" 이지만 PHP `(int)` 변환 때문에 `3a` · `3.7` 은 `3` 이 되어 난이도 3 결과가 **경고와 함께** 나온다. `abc` · `0` · `6` 은 0건(DB 에 1~5 외 값이 없다는 전제 — 스키마에 CHECK 제약은 없음, `01-schema.sql:25`). 요약에는 변환된 값이 `"난이도 " . (int)$level` 로 붙어(`search.php:229`) `abc` 는 화면에 "난이도 0" 으로 보인다 — 빈 값일 때(BR-10) 요약이 비는 것과 대조된다.

### BR-13 태그는 태그 이름 정확 일치 (1개)
- **규칙**: 태그를 앞뒤 공백 제거 후 비어 있지 않으면, 그 이름의 태그가 연결된 문항만 찾는다.
- **근거**: `search.php:235-236`, `search.php:244-247`
- **근거 코드**:
  ```php
  $where .= " AND EXISTS (SELECT 1 FROM item_tag it JOIN tag t ON t.id = it.tag_id"
          . " WHERE it.item_id = v_item_public.id AND t.name = ?)";
  ```
- **확신도**: 확실
- **비고**: 태그 **id** 가 아니라 **name** 으로 검색한다(등록은 id 를 받는다, BR-36).

### BR-14 태그 50자 초과 시 잘라서 검색
- **규칙**: 태그 이름이 50자를 넘으면 앞 50자만 쓰고 경고를 표시한다.
- **근거**: `search.php:240-242`
- **근거 코드**:
  ```php
  if (mb_strlen($tag, 'UTF-8') > 50) {
      $tag = mb_substr($tag, 0, 50, 'UTF-8');
  ```
- **확신도**: 확실
- **비고**: 매직 넘버 `50` — 컬럼 `tag.name VARCHAR(50)`(`01-schema.sql:37`)과 같은 값을 코드에 따로 적었다.

### BR-15 태그의 `%` · `_` 는 부분 일치로 쓰이지 않음
- **규칙**: 태그에 `%` 또는 `_` 가 있으면 경고만 표시하고 정확 일치(`=`)로 조회한다.
- **근거**: `search.php:237-238`, `search.php:245`
- **근거 코드**:
  ```php
  if (strpos($tag, '%') !== false || strpos($tag, '_') !== false) {
      $warnings[] = '태그는 부분 일치를 지원하지 않습니다.';
  ```
- **확신도**: 확실
- **비고**: 키워드(BR-06)와 달리 와일드카드가 동작하지 않는다.

### BR-16 등록되지 않은 태그여도 조회는 그대로
- **규칙**: 태그 이름이 `tag` 테이블 목록에 없으면 경고를 표시하고 조회는 그대로 한다.
- **근거**: `search.php:250-260`
- **근거 코드**:
  ```php
  if ($opt['value'] !== '' && $opt['value'] === $tag) {
  ...
      $warnings[] = '등록되지 않은 태그입니다: ' . $tag;
  ```
- **확신도**: 확실
- **비고**: 등록 여부 확인은 PHP `===`(대소문자 구분), 실제 조회는 `tag` 테이블의 `_ci` 콜레이션(`01-schema.sql:40`)이라 대소문자만 다른 태그는 "등록되지 않은 태그" 경고와 함께 결과가 나올 것으로 **추정**(실행 확인 필요).

## 2. 문항 검색 — 정렬 (`search.php`)

### BR-17 기본 정렬은 난이도 내림차순, 같으면 id 오름차순
- **규칙**: 정렬 기준(`sort`)이 비어 있으면 `level DESC, id ASC` 로 정렬한다.
- **근거**: `search.php:317-320`
- **근거 코드**:
  ```php
  case '':
      // 기본 정렬: 어려운 문항부터, 같은 난이도면 번호 순
      $orderBy = " ORDER BY level DESC, id ASC";
  ```
- **확신도**: 확실
- **비고**: 주석과 코드 일치. 기본 검색(BR-10)과 겹치면 가장 어려운 난이도 5 가 빠진 상태에서 난이도 4 부터 나온다.

### BR-18 알 수 없는 정렬 기준은 기본 정렬
- **규칙**: `sort` 가 `id` · `title` · `unit` · `level` · `created` 가 아니면 경고를 표시하고 기본 정렬(BR-17)을 쓴다.
- **근거**: `search.php:322-326`
- **근거 코드**:
  ```php
  default:
      $warnings[] = '알 수 없는 정렬 기준입니다. 기본 정렬을 사용합니다.';
      $orderBy = " ORDER BY level DESC, id ASC";
  ```
- **확신도**: 확실
- **비고**: `ORDER BY` 는 `switch` 의 고정 문자열로만 만들어진다(ARCHITECTURE.md 6절 미확인 "`$orderBy` 가 화이트리스트로만 만들어지는지" → 확인됨). 기본 정렬 문자열이 `:319` · `:325` 두 곳에 중복돼 있다.

### BR-19 정렬 파라미터는 대소문자 · 공백 무시
- **규칙**: `sort` · `dir` 는 앞뒤 공백을 제거하고 소문자로 바꿔 판단한다.
- **근거**: `search.php:266-267`
- **근거 코드**:
  ```php
  $sort = strtolower(trim($sort));
  $dir  = strtolower(trim($dir));
  ```
- **확신도**: 확실
- **비고**: 단원 코드(BR-09)는 대소문자를 바꾸지 않는 것과 대조된다.

### BR-20 잘못된 정렬 방향은 무시
- **규칙**: `dir` 가 `asc` · `desc` 가 아니면(비어 있지 않을 때) 경고를 표시하고 방향을 지정하지 않은 것으로 처리한다.
- **근거**: `search.php:268-273`
- **근거 코드**:
  ```php
  if ($dir !== 'asc' && $dir !== 'desc') {
      if ($dir !== '') {
          $warnings[] = '정렬 방향은 asc 또는 desc 만 가능합니다.';
  ```
- **확신도**: 확실

### BR-21 정렬 기준별 기본 방향

### BR-44 단원별 문항 수는 공개(A) 문항만 센다
- **규칙**: 단원 목록의 문항 수는 `status = 'A'` 인 문항만 센다(삭제 · 검수중 제외).
- **근거**: `units.php:17`
- **근거 코드**:
  ```php
  (SELECT COUNT(*) FROM item i WHERE i.unit_id = u.id AND i.status = 'A') AS item_count
  ```
- **확신도**: 확실
- **비고**: 주석(`units.php:15`)과 코드 일치. **같은 "공개" 판정이 두 곳에 다르게 구현** — 검색은 뷰(`01-schema.sql:70`), 단원 목록은 `item` 직접 조건(`units.php:17`). 문항이 없는 단원도 0으로 표시된다.

### BR-45 단원 목록은 학년 → 코드 순
- **규칙**: 단원 목록 · 등록 폼 단원 선택 · 검색 폼 단원 선택은 모두 `grade ASC, code ASC` 로 정렬한다.
- **근거**: `units.php:19`, `register.php:27`, `search.php:156`
- **근거 코드**:
  ```php
  ORDER BY u.grade ASC, u.code ASC                                             // units.php:19
  $res = $conn->query("SELECT id, code, name FROM unit ORDER BY grade ASC, code ASC");   // register.php:27
  ```
- **확신도**: 확실
- **비고**: 같은 정렬이 세 곳에 복붙돼 있다. 검색 폼은 학년별 `optgroup` 으로 묶는다(`search.php:452-462`). 결과 표의 `sort=unit`(BR-23)은 학년을 보지 않는다.

### BR-46 태그 목록은 id 순
- **규칙**: 등록 폼 태그 체크박스와 검색 폼 태그 선택은 `tag.id ASC` 로 정렬한다.
- **근거**: `register.php:34`, `search.php:178`
- **근거 코드**:
  ```php
  $res = $conn->query("SELECT id, name FROM tag ORDER BY id ASC");
  ```
- **확신도**: 확실
- **비고**: 이름순이 아니다.

## 7. 문항 수정 — 코드 없음

- `legacy/item-bank-php/` 전체에서 쓰기 SQL 은 `INSERT INTO item`(`register.php:93`)과 `INSERT INTO item_tag`(`register.php:105`) 뿐이다. `UPDATE` · `DELETE` 문이 없다.
- 따라서 **수정 시 검증 규칙은 이 모듈에서 뽑을 수 없다.** 등록 검증(BR-31 ~ BR-36)을 수정에도 적용할지, `status` 전이(`R → A`, `A → D`)를 누가 하는지는 미확인이다(ERD.md 5절과 같음).
