# 배치 점검

로그 폴더: `$ARGUMENTS`. 비어 있으면 `pipeline-samples/batch-logs` 를 쓴다.
건수 CSV: 로그 폴더의 상위 폴더에 있는 `datamart-counts.csv`. 없으면 사용자에게 경로를 묻는다.

## 점검 기준
1. 실행 여부: 다른 날에는 매일 돌던 job 이 그날 로그에 없거나, START 만 있고 종료(SUCCESS · FAIL) 기록이 없으면 이상. CSV 에 그날 · job 행이 없는 것도 근거로 붙인다.
2. 중복 실행: 같은 날 같은 job 의 SUCCESS 가 두 번 이상이면 이상.
3. 적재 건수: 같은 job 의 직전 7일 평균에서 ±30% 넘게 벗어나면 이상. 직전 데이터가 7일이 안 되면 있는 날만으로 평균을 내고 그렇다고 적는다. 0건은 무조건 이상.
4. 지연: 소요 시간이 그 job 의 평소 소요 시간(전체 기간 중앙값)의 2배를 넘으면 이상. `elapsed=` 가 없으면 같은 run_id 의 START~SUCCESS 시각 차이를 쓴다.

## 작업 규칙
- 로그를 통째로 읽지 않는다. `grep -n` · `awk` · `wc` 로 START · SUCCESS · FAIL · WARN · ERROR 줄만 뽑고, 이상 후보 주변만 `sed -n` 으로 본다.
- 평균 · 편차 · 중앙값 · 배수는 암산하지 않는다. 명령이나 스크립트로 계산하고, 스크립트는 `$CLAUDE_JOB_DIR/tmp` 같은 임시 폴더에 둔다.
- 근거 표기: 로그는 `batch-logs/<파일>:<줄번호>`, 건수는 `datamart-counts.csv:<줄번호>` 와 그 행 값.
- 로그에 없는 원인은 추측하지 않는다. 원인은 "확인 필요"로 두고 무엇을 더 봐야 하는지만 적는다. 로그에 적힌 메모(예: replica lag)는 "로그 메모"로 인용만 한다.
- 영향 추정은 로그 · CSV 에 보이는 범위에서만 쓰고, 확인되지 않은 추정이라고 밝힌다.
- 운영자 이메일 · 학생 식별자(`STU-…`) · 토큰은 보고서에 옮기지 않는다.

## 진행 순서
1. 먼저 결과를 표(날짜 / job / 점검 항목 / 근거)로 답변에 보여 준다.
2. 이상이 한 건도 없으면 파일을 만들지 않고 "이상 없음" 한 줄만 답한다.
3. 이상이 있으면 `docs/batch-check/report.md` 로 저장한다. 파일이 이미 있으면 덮어쓰기 전에 묻는다.

## 리포트 형식 (docs/batch-check/report.md)
- 맨 위 요약 한 줄: 점검 기간, 이상 건수(해당 날짜 수).
- 계산 기준: 평균 · 중앙값을 어떻게 냈는지, job 별 중앙값.
- 이상 목록 표: 날짜 / job / 점검 항목 / 근거 / 영향 추정 / 다음 확인 사항.
- 맨 아래 "이상 없음으로 판정한 날짜" 목록.
