# 장애 원인 분석(RCA)

대상은 `incident-logs/$ARGUMENTS/`, 결과는 `docs/rca/$ARGUMENTS.md` 다. 모든 시각은 KST 로 맞춰 적는다.

## 절차

1. **수집 범위** — 파일을 통째로 읽지 않는다. `wc -l` · `head` · `tail` · `grep -c` 로 파일별 줄 수, 기록 기간, 시각 형식, 타임존부터 표로 정리한다.
   - 타임존 표기가 없는 파일은 다른 파일의 같은 사건(같은 요청 · 같은 client)과 초 단위로 맞춰 판단하고, epoch 값이 있으면 변환해 확인한다. 판단 근거와 KST 변환 규칙을 적는다.
   - 분 단위로 오류 · 경고 · 5xx 를 집계해 이상 구간을 정하고, 앞 30분 · 뒤 10분을 붙여 분석 구간으로 삼는다. 이 단계에서는 원인을 추정하지 않는다.
2. **타임라인** — 분석 구간의 사건을 시간순 표로 적는다. 모든 줄에 출처 `파일:줄번호` 를 단다.
   - 로그에 있는 사건만 적고 해석은 하지 않는다. 반복 사건은 "첫 시각, 이후 N건/분" 으로 묶는다.
   - 파일 간 시각 차가 몇 초 이내면 "(선후 불확실)" 로 표시한다.
   - 가장 많이 나온 오류보다 **앞선** 평소와 다른 줄(느린 쿼리 · 경고 · 재시작 · 설정 재적재 · 트래픽 변화)을 점검표로 확인한다. 없으면 무엇을 grep 했는지 적고 "로그에 없음" 으로 쓴다.
3. **가설** — 증상(결과)과 설명해야 할 관찰을 먼저 나눈 뒤, 서로 다른 계층(코드 · DB · 트래픽 · 인프라 · 배포/설정)에서 가설을 2개 이상 세운다. 가설마다 지지 근거, **반증 조건**, 확인 방법(실행할 명령)을 적는다.
4. **반증과 판정** — 로그로 확인할 수 있는 것부터 실행해 반증을 시도하고, 실행한 명령과 숫자를 기록한다.
   - 남은 단서를 코드(장애 당시 커밋, `git show <커밋>:<경로>`) · 설정과 대조한다.
   - 가설마다 **유지(채택) · 기각 · 판단 불가(로그 부족)** 로 판정하고, 판단 불가면 필요한 로그를 적는다.
   - 운영 DB · 운영 서버 확인은 직접 접속하지 않고 담당자에게 요청할 명령으로 남긴다.
5. **리포트 작성** — 다음 절을 갖춘다.
   - 요약(무엇 · 언제 · 직접 원인 · 배경 원인 · 확신 수준 · 조치 상태)
   - 원인(배경 원인 · 직접 원인과 진행)
   - 근거 로그 줄(문장 ↔ `파일:줄번호` ↔ 발췌)
   - 수정안(지금 당장 적용할 것)
   - 재발 방지(같은 유형을 구조적으로 막는 장치)
   - 모니터링 항목(지표 · 임계값 · 이번 장애에서 처음 넘은 시각)
   - 확인하지 못한 것(무엇을 · 왜 못 했고 · 누가 확인할 수 있는지)
6. **마스킹** — 리포트를 저장하기 전에 [masking-rules.md](masking-rules.md) 의 규칙을 적용한다. 저장 후 그 파일의 점검 명령으로 남은 값이 0건인지 확인한다.

## 하지 말 것

- 로그에 없는 줄을 인용하지 않는다. 발췌는 해당 줄을 `sed -n '<줄>p'` 로 다시 확인한 것만 쓴다.
- 가장 많이 나온 오류를 곧바로 원인이라고 부르지 않는다. 그것은 증상이고, 질문은 "왜 그 상태가 되었나" 다.
- 원본 로그(`incident-logs/`)와 소스 코드를 수정하지 않는다.
- 마스킹 대응표(원래 값 ↔ 별칭)를 파일로 남기지 않는다.
- 마스킹 전 원본을 임시 폴더에 복사해 두지 않는다.
