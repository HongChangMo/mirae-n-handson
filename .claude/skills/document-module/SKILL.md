# 레거시 모듈 문서화

## 원칙
- 분석 대상 폴더(`$ARGUMENTS` 의 모듈 경로)의 파일은 읽기만 한다. 수정 · 생성 · 삭제하지 않는다.
- 쓰는 곳은 `docs/<모듈명>/` 뿐이다. `<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다.
  - `legacy/item-bank-php` → `item-bank` / `legacy/assignment-thymeleaf` → `assignment` / `legacy/grade-mssql` → `grade`
  - 셋에 없는 경로면 멈추고 모듈명을 묻는다.
- 범위 제한 인자가 있으면 그 파일 · 기능만 보고, 문서 머리에 범위를 적는다.
- 단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다. 저장 없이 다음 단계를 시작하지 않는다.
- 모든 주장에 `파일:줄번호` 를 단다. 근거를 못 대면 "미확인"으로 남긴다.

## 0. 계획 먼저 제시
- 대상 폴더의 파일 목록과 줄 수, 스키마 · 시드 파일 위치를 확인한다.
- 단계별로 볼 파일, 만들 산출물, 범위 밖으로 둘 것을 표로 보여 주고 승인을 받은 뒤 시작한다.

## 1. 진입점 → `ARCHITECTURE.md`
- 요청을 받는 곳(페이지 · 컨트롤러 · 라우트 · 프로시저)과 입력 파라미터를 목록으로 적는다.

## 2. 의존 관계 → `ARCHITECTURE.md` 에 추가
- include · import · 호출 관계를 "호출하는 쪽 → 호출되는 쪽" 방향으로 적는다. 방향은 실제 호출문 줄로 확인한다.
- DB 객체(테이블 · 뷰 · 프로시저) 참조를 파일별로 모은다.

## 3. 데이터 흐름 → `ERD.md`
- 테이블 · 컬럼 · PK/FK · 제약 · 콜레이션을 스키마 파일에서 옮기고 mermaid `erDiagram` 으로 그린다.
- 진입점별로 입력 → 가공 → SQL → 출력 흐름을 적는다. 읽기 · 쓰기 SQL 을 구분하고, 없는 쓰기(UPDATE · DELETE)는 "없음"으로 명시한다.

## 4. 비즈니스 규칙 후보 → `BUSINESS-RULES.md`
- 조건문 · SQL · 뷰 정의 · 스키마 제약에서 뽑는다. 영역별로 묶고 맨 위에 요약 표를 둔다.
- 규칙 하나는 아래 형식을 그대로 쓴다.

```markdown
### BR-01 <규칙 이름>
- **규칙**: <무엇을 · 언제 · 어떻게 — 한두 문장>
- **근거**: `search.php:522`, `db/mariadb/init/01-schema.sql:70`
- **근거 코드**:
  ```php
  <근거 줄을 그대로 인용>
  ```
- **확신도**: 확실(조건문 · SQL 로 확인) / 추정(이름 · 주석 · 설정으로 짐작)
- **비고**: 주석과 코드 불일치, 중복 구현, 매직 넘버, 이관 시 결정 필요 사항
```

- 주석에만 있는 내용은 규칙으로 올리지 않고 별도 절(주석 · 스키마 주석에만 있는 내용)에 모은다.
- 매직 넘버 표, "이관 전 사람이 결정할 것" 표, 빈 "검증 이력" 표(날짜 · 규칙 · 변경 내용 · 계기)를 끝에 둔다.

## 하지 말 것 (item-bank 검증 이력에서 실제로 틀렸던 유형)
- **조건의 한쪽 가지만 읽기** — BR-26 은 `else if ($pageRaw !== '' && ...)` 의 `!== ''` 를 놓쳐 빈 값도 경고가 난다고 적었다.
  `if / else if / else` 는 모든 가지와 복합 조건의 각 항을 따로 확인하고, 죽은 조건도 비고에 적는다.
- **전처리가 다른 파라미터를 같게 취급하기** — `page` 만 trim 하지 않는 것을 놓쳤다. 파라미터마다 trim · 형변환 · 소문자화를 따로 확인한다.
- **애플리케이션 코드만 보고 대소문자 · 비교 동작 단정하기** — BR-08 · BR-16 은 DB 콜레이션(`_ci`)을 근거에 넣지 않았다.
  문자열 일치 규칙에는 해당 테이블 · 컬럼 콜레이션 줄을 근거로 붙이고, 실행 확인 전에는 "추정"으로 둔다.
- **느슨한 비교 · 형변환의 결과 추적 생략** — BR-10 의 `==`, BR-12 의 `(int)` 가 요약 표시(`abc` → "난이도 0")까지 바꾸는 것을 놓쳤다.
  `==` · `(int)` · `(string)` 이 있으면 조회 조건뿐 아니라 화면 표시 · 경고 문구에 미치는 영향까지 따라간다.
- **규칙의 귀결 빼먹기** — BR-10 에서 "난이도 5 는 `level=5` 를 명시해야만 조회된다"는 귀결을 적지 않았다. 제외 규칙은 그 데이터가 어디서 다시 보이는지까지 적는다.
- 공통: 존재하지 않는 함수 · 파일을 근거로 들지 않는다(인용 전 해당 줄을 다시 연다). 코드에 없는 규칙을 주석 · 이름만 보고 만들지 않는다.

## 5. 마지막 — 사람이 표본 점검할 규칙 3개 추천
- 답변 끝에 3개를 추천하고 각각 추천 이유와 확인 방법(열어 볼 `파일:줄번호`, 실행해 볼 입력값)을 적는다.
- 3개 중 1개는 **가장 그럴듯한(틀려도 눈치채기 어려운) 규칙**으로 고른다. 나머지는 "추정" 규칙, 주석과 코드가 어긋난 규칙을 우선한다.
- 사람이 점검한 결과로 규칙을 고치면 "검증 이력" 표에 한 줄씩 남긴다.
