# AI 검증루프 v1

> **v1 · 2회차** (2026-10-06)
> 1. 판정 기준(§6)의 주관적 문장 두 개를 지우고, `templates/approval-checklist.md` v1 의 [반려] · [경고] 항목으로 판정하게 했다.
> 2. 기준 결과에 "확인 필요"를 추가했다(충족이 아님). 바뀐 코드 폴더가 없을 때와 web lint · typecheck · characterization 실행 조건을 절차에 적었다.
> 3. 심각도를 치명 / 주요 / 경고 / 제안 네 단계로 나누고, 교차 검증 대상을 치명 묶음 A~D 에 해당하는 변경으로 정했다.

AI 가 만든 변경분과 외주사 PR 을 머지하기 전에 거치는 절차다. **만든 쪽과 검증하는 쪽을 분리**하고, 판정은 `templates/approval-checklist.md` 의 네 기준으로 한다.

## 1. 왜 분리하나

만든 세션은 자기 코드를 옹호한다. 같은 컨텍스트 안에서 "잘 됐는지 확인해 주세요"라고 물으면 만든 이유를 다시 설명받을 뿐이다. 검증은 **변경분만 보는 새 컨텍스트**에서 한다.

## 2. 패턴

| 패턴 | 방법 | 쓰는 때 |
|---|---|---|
| 만든 세션 → 리뷰 세션 | 새 터미널에서 Claude Code 를 새로 띄워 diff 만 보게 한다 | 기본. 모든 변경 |
| Claude 생성 → 다른 모델 리뷰 | 새 터미널에서 `claude --model sonnet` 처럼 다른 모델로 새 세션을 띄워 같은 diff 와 체크리스트를 넘긴다 | 교차 검증. 치명 묶음 A~D 에 해당하는 파일(DB 설정 · 쿼리 · 트랜잭션 · 외부 연동 · 로그)을 바꾼 변경 |
| 리뷰어 Sub-agent | 읽기 전용 리뷰어를 `.claude/agents/` 에 정의해 두고 위임한다 | 같은 세션 안에서 격리된 컨텍스트로 리뷰할 때 |

## 3. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 만든 세션 | 구현, 테스트 작성, 리뷰 결과 반영 | 자기 변경의 승인 판정 |
| 리뷰 세션 | diff 읽기, 체크리스트 대조, 테스트 실행, 이슈 목록과 판정 | **코드 수정.** 고치기 시작하면 그 순간 "만든 쪽"이 된다 |
| 사람 | 요청 범위 확정, 리뷰 이슈의 수용 · 기각, 최종 머지 | 리뷰어의 판정을 읽지 않고 머지 |

## 4. 절차

1. **요청 범위 확인.** 무엇을 요청했는지 한 문장으로 받는다. 범위가 주어지지 않았으면 판정하지 말고 먼저 묻는다.
2. **변경 파일 목록과 diff 읽기.** `git diff --stat <범위>` 로 목록을 먼저 보고, 파일마다 diff 를 읽는다. patch 파일이면 `git apply --stat` 으로 목록을 뽑는다.
3. **체크리스트 대조.** `templates/approval-checklist.md` 를 읽고 항목마다 예 · 아니오 · 확인 필요 중 하나로 답한다. [반려] · §2 항목의 "아니오"는 그 기준을 미충족으로 만들고, [경고] 항목의 "아니오"는 경고 이슈가 된다.
4. **테스트 실행.** 변경된 모듈의 테스트만 실행한다. 어느 명령을 쓰는지는 팀 `CLAUDE.md` 의 빌드 · 테스트 명령을 따른다. `modern/web` 이면 `npm run lint` · `npm run typecheck` 도 실행하고, 이관 · 리팩토링 변경이면 `characterization` 의 `npm test` 도 실행한다. 바뀐 코드 폴더가 없으면 실행하지 않고 테스트 기준을 "확인 필요"로 적는다. 결과는 통과 · 실패 수와 실패한 테스트 이름만 남기고 전체 로그를 대화에 싣지 않는다.
5. **판정.** 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다. 하나라도 미충족 또는 확인 필요이면 반려.
6. **되돌리기.** 리뷰 결과를 만든 세션에 넘긴다. 만든 세션은 이슈마다 수용 · 기각을 사람과 정한 뒤 수용한 것만 고치고, 다시 2번부터 돈다.

## 5. 출력 형식

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 / 확인 필요 | 실행 명령과 통과 · 실패 수 |
| 치명 이슈 0건 | 충족 / 미충족 / 확인 필요 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 / 확인 필요 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 / 확인 필요 | 위반 항목 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
```

- 이슈 한 건은 심각도(치명 / 주요 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 네 항목을 모두 채운다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 따로 적는다.

## 6. 판정 기준 (v1)

항목 문장은 `templates/approval-checklist.md` 에 있다. 기준별 반려 조건은 다음과 같다.

- **테스트 통과** — 테스트를 실행하지 않았거나, 실패 · 오류가 1건 이상이거나, `modern/api` 의 새 public 메서드(접근자 · 생성자 제외) · 새 엔드포인트 · 본문이 바뀐 public 메서드에 그것을 호출하는 테스트가 없으면 반려.
- **치명 이슈 0건** — 치명 묶음 A(비밀값 · SQL · DB 접속) · B(데이터 손실) · C(개인정보 로그) · D(트랜잭션 풀 고갈) 중 1건이라도 있으면 반려.
- **요청 범위 이탈 없음** — 요청 기능이 diff 에 없거나, 사유가 적히지 않은 범위 밖 파일이 있거나, 요청에 없는 의존성 · 스키마 · 설정 변경이 있으면 반려. 사유가 적힌 범위 밖 파일은 경고. 요청 기능 파일 안의 포맷 · import 정리는 이슈가 아니다.
- **컨벤션 준수** — 계층 구조 · 예외 처리 · 금지 구문([반려] 항목) 위반이 있으면 반려. 네이밍 · 형식 · 테스트 형식([경고] 항목) 위반은 경고.
- 경고는 승인을 막지 않는다. "확인 필요"는 충족이 아니다. diff 밖에 원래 있던 위반은 제안으로만 적는다.

## 7. 하지 말 것

- 리뷰 세션은 코드를 수정하지 않는다. 보고만 한다.
- 테스트를 실행하지 않고 "통과"라고 쓰지 않는다. 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실을 적고 사람에게 기동을 요청한다.
- 요청 범위를 모르는 상태에서 "범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈 0건이 나오면 "경고 · 제안 수준까지 다시 봐 달라"고 한 번 더 요청한다. 0건은 결과일 수도, 안 본 것일 수도 있다.
